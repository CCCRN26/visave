# Open product and architecture decisions

Resolve decisions 1–5 before committing to the production mobile architecture. The recommended defaults optimize for a safe, useful member-first release and do not change current backend behavior by themselves.

| # | Decision | Why it matters | Recommended default | Backend impact | Mobile impact |
|---:|---|---|---|---|---|
| 1 | Supported platforms: Android only, or Android + iOS? | Device testing, distribution, cookie behavior, secure storage, links, permissions, and release effort differ. | Android-first pilot, while keeping code portable to iOS. Confirm the target community's device mix. | Test/auth contracts on every supported platform; no API redesign solely for Android. | Platform build profiles, physical-device matrix, store accounts, and platform-specific secure/cookie testing. |
| 2 | React Native framework and core libraries? | A shared foundation prevents incompatible networking/session decisions. | Expo-managed React Native + TypeScript + Expo Router + TanStack Query (or an agreed equivalent). | None unless the chosen network stack exposes a backend incompatibility. | Establish navigation, typed API layer, server-state caching, SecureStore, error boundary, and redacted telemetry. |
| 3 | Member-first or multi-role V1? | Multi-role includes high-risk finance, signatures, PA/MM policy, and SOD rules. | **Member-first.** Add operator roles only in later, separately accepted milestones. | Existing self-service APIs suffice except auth blockers; aggregate dashboard optional. | Smaller navigation/permission surface and safer release. |
| 4 | Retain cookie sessions or add mobile access/refresh tokens? | This decides credential storage, restoration, logout, binary downloads, and security review. | Run a time-boxed physical-device cookie proof. If any required behavior is unreliable, build a dedicated revocable/rotating mobile token contract. | Potential new auth/session endpoints and tables; preserve eight-hour/revocation/password-change behavior. | Cookie jar versus SecureStore/Keychain/Keystore transport; centralized 401/logout handling. |
| 5 | How will native login obtain a Turnstile token? | The current web DOM widget cannot run directly in a native view, while the server requires a verified action/hostname. | Security-reviewed constrained WebView/browser challenge on an allowed HTTPS origin, unless backend/security selects another Cloudflare-supported architecture. Never bypass it. | May require a token hand-off/bootstrap route or approved hosted challenge; server Siteverify remains mandatory. | WebView/browser lifecycle, navigation allow-list, token hand-off, accessibility, expiry and retry UX. |
| 6 | Offline policy: cached reads or transaction sync? | Financial state and meeting lifecycles make stale replay dangerous. | Read-only cached snapshots with online refresh; no queued writes. | None for V1. Later sync needs versions/conflicts/idempotency/replay contracts. | Cache timestamps, offline labels, reconnect revalidation, disabled mutations offline. |
| 7 | Are native push notifications required in V1? | Only database in-app notifications exist. | No; poll on focus/pull-to-refresh for V1. | If yes: device registration/storage, preferences, provider integration, token cleanup and delivery observability. | Permission UX, Expo/FCM/APNs token lifecycle, safe payload/deep links. |
| 8 | Should biometric local unlock be offered? | Biometrics protect local convenience, not the server session, and can complicate recovery. | Defer until auth transport is stable; if added, gate local credential access only. | None. | SecureStore/Keychain access-control behavior, fallback, device change and logout handling. |
| 9 | How should PDF and Excel reports be handled? | Downloads contain private financial/member data and Excel has weak member-V1 value. | Native JSON views plus opt-in PDF view/share; defer Excel UI. | Optional future JSON report/statement endpoint; existing binary routes remain. | Authenticated binary download, app-private temporary files, MIME checks and deletion. |
| 10 | Google Meet external launch or deep/universal links? | External launch is supported now; custom routing increases platform configuration and test scope. | Open the authorized HTTPS `joinUrl` externally with browser fallback. | None for V1. | URL allow-list, app/browser fallback. Add app/universal-link setup only for confirmed inbound-link use cases. |
| 11 | Will operator mobile capture signatures/camera files? | Reconciliation signatures are privileged, sensitive, and tied to online financial close. | Exclude from member V1; use signature-pad PNG only in a later online-only operator phase. | Existing PNG data-URL contract may suffice; review upload ergonomics/limits before operator release. | Signature UX, temporary-memory hygiene, accessibility, permission minimization; camera is not currently required by the contract. |
| 12 | Pilot/distribution/support model? | Internal testing, app-store release, signing ownership, staged rollout, telemetry and incident response must be settled before production. | Closed Android pilot against staging, then managed production rollout after blocker sign-off; collect privacy-minimized crash/performance telemetry. | Confirm environment URLs, rate-limit/storage readiness, support correlation/observability and release compatibility policy. | Package IDs, signing/EAS ownership, tester channel, version gating, privacy disclosures and rollback plan. |

## Decision record template

For each decision record: owner, date, chosen option, rejected alternatives, threat/privacy considerations, backend work item, mobile work item, staging evidence, and production acceptance. A verbal choice is not sufficient for decisions 4 and 5.
